# Rombot 交接说明（比赛主链路 + 接口）

面向：拿到本仓库后需要快速跑通、定位瓶颈并继续优化的同学。  
分支建议：`feature/ark-seedream-hunyuan-pipeline`  
范围：`backend/` + `frontend/`；根目录 `room_scan_standalone/` **不在本交接主链路内**（本地调试目录，默认 gitignore）。

---

## 1. 产品在做什么

当前是 **FastAPI + Vite / React / TypeScript + Three.js 的同域比赛应用**。生产式演示由
FastAPI 同时提供 `/api/*`、静态资源和 `frontend/dist` SPA，入口为
`http://127.0.0.1:8000`。

比赛热路径：

```text
/space 上传 room1–7 原图
  → 浏览器计算 SHA-256，与预处理户型 manifest 匹配 sceneId（图片不上传）
  → /feed?sceneId=... 浏览视频
  → 暂停后以 videoId + time + frameHash 命中离线 analysis.json
  → 仅带有预生成 GLB 的家具 Tag 可点击
  → /space?sceneId=...&frameId=...&objectId=...
  → 同一 Three.js 场景加载户型白模与家具 GLB
  → 家具尺寸归一、移动、旋转、缩放 + 3×3 射线自动墙体剖面
```

这条链路的关键约束是：**比赛过程中不调用 Ark 户型重建，不实时检测，不调用
Seedream，也不现场生成 3D**。演示稳定性依赖预设 manifest、离线 `analysis.json` 和缓存
`generated_model.glb` 的完整性。

仓库仍保留两类冷路径，供赛后或开发调试使用：

1. `POST /api/floorplan/reconstruct`：Ark 解析真实户型图，再由本地 Builder 生成白模 GLB。
2. `detect → select-object`：实时家具检测、裁剪、视觉 brief、Seedream 参考图和
   Hunyuan / Tripo Image-to-3D。

冷路径当前已验证的 Provider 组合：

```text
DETECTION_PROVIDER=ark_grounding
SEGMENTATION_PROVIDER=mock          # bbox crop，可不接 SAM
MODEL3D_PROVIDER=feature_tripo      # 或 feature_hunyuan
```

内部 3D 子链（`feature_*` provider）：

```text
Ark 视觉 brief（或复用检测阶段 visualFeatures）
  → 每个 CLIP 去重候选调用一次 Ark 尺寸估算并写入固定米制初始尺寸
  → Seedream 从去重候选 crop 生成单张 45° 左前产品参考图
  → Hunyuan / Tripo 以该参考图为单图输入
  → 轮询拿 GLB，缓存到 outputs/
```

房间扫描 `POST /api/room/scan` 仍是 **mock 场景**，不属于当前比赛热路径。

## 3. 功能脉络（按调用顺序）

### A. 比赛热路径：上传并选择预处理户型

1. 访问 `/space`，选择或拍摄一张 `room1–7` 原始户型图；接受 JPEG / PNG / WebP，前端限制 15 MB。
2. `sha256File()` 在浏览器计算文件 SHA-256，同时请求 `GET /api/floorplan/presets`。
3. 用 `sourceSha256` 精确匹配预设；图片本身不上传，也不调用 `/api/floorplan/reconstruct`。
4. 匹配成功得到 `sceneId`：
   - 没有待放置家具时进入 `/feed?sceneId=<sceneId>`。
   - 已从 Feed 选中家具但缺少户型时，保留原查询参数并补上 `sceneId`，返回 `/space`。
5. 未命中时停留在上传步骤并提示改用 `room1–7` 原图，不回退到 Ark 实时重建。

### B. 比赛热路径：Feed 暂停识别与可点击 Tag

1. Feed 保留查询参数中的 `sceneId`。
2. 视频暂停后，浏览器计算暂停画面的 64-bit dHash，并调用 `POST /api/feed/detect`，传入
   `videoId + time + frameHash`。
3. 后端从该视频 `analysis.json` 中定位暂停时间前后帧，再用 dHash 距离选出更相似的一帧；
   不上传完整暂停截图，也不调用实时检测 Provider。
4. 响应对象只有存在 `prebuiltGlbUrl` 时 Tag 才可点击；没有预生成 GLB 的 Tag 显示“模型准备中”。
5. 点击可用 Tag 后进入：

```text
/space?sceneId=<sceneId>&videoId=<videoId>&time=<time>
       &sceneType=<sceneType>&frameId=<frameId>
       &objectId=<objectId>&objectLabel=<label>
```

如果此前没有选择户型，则不带 `sceneId` 进入 `/space`，先完成户型匹配，再保留其余参数继续。

### C. 比赛热路径：Space 组合预览与编辑

1. Space 并行请求：
   - `GET /api/floorplan/presets/{sceneId}` 恢复户型白模。
   - `GET /api/feed/prebuilt-asset?frameId=...&objectId=...` 恢复缓存家具及估算尺寸。
2. `FloorplanViewer` 在同一个 Three.js Scene 中加载两份 GLB。
3. 若家具带 `estimatedDimensions`，按宽/高/深对 GLB 做三轴尺寸归一；否则按户型尺度给统一兜底缩放。
4. 家具落到地面后可沿 X/Z 移动、绕 Y 轴旋转、等比缩放，移动范围限制在户型包围盒内。
5. 相机使用 OrbitControls。视角变化时用屏幕 3×3 共 9 条射线找出遮挡视线的墙；候选至少需
   2 条首命中射线，并结合墙面夹角、覆盖率、距离和切换滞回选墙，约 180 ms 淡出。俯视角恢复全部墙体。
6. 新 Builder GLB 优先读取 `extras.rombotKind/wallId`；比赛旧白模通过
   `wall_*_block_*` 节点名和几何邻近关系兼容墙体、门窗分组。

### D. 测试页串联流程（无外部 AI 也可体验）

`/static/pipeline-test.html` 将原识别/3D 流程与后续两项能力串在同一页：

```text
图片或视频暂停识别
  → 视频优先直接读取已有 analysis.json，不触发 Provider
  → 选择家具
  → 有 prebuiltGlbUrl 时直接加载缓存 GLB；否则保留实时生成入口
  → POST /api/product/mock-search 返回明确标记 isMock=true 的 Top 3
  → 输入演示位置 X/Z/旋转
  → POST /api/room/placement-check（enableAgents=false）
  → 展示 4 项真实几何检查 + 确定性建议移动坐标
```

Mock 边界必须保持清晰：商品是固定类别目录，不是 CLIP/IKEA 真实检索；房间使用
`demo_living_room` mock 场景，不是用户上传的白模；空间检查和 `moves` 使用真实几何规则，
且关闭 Agent，不调用 Ark 文本模型。该页用于先验证交互顺序，尚未完成 Space 坐标/场景接入。

### E. 冷路径：实时 Feed（前端暂停视频 / 上传帧）

1. `POST /api/feed/detect`  
   - 若已有 `outputs/videos/<videoId>/analysis.json` → 走暂停帧匹配，**不调实时检测模型**  
   - 暂停帧匹配逻辑：前端传入 16 位 `frameHash` + 暂停时间 `time`；后端只在该视频 analysis 的“前一帧 / 后一帧”里二选一，用 64-bit dHash 选择更相似的那一帧，不上传完整暂停截图。
   - 若 dHash 距离相同，选时间更近者；若仍完全相同，选前一帧。
   - 返回的是匹配帧已有的 bbox / tagPosition / 去重候选 crop / `frameImageUrl`，不会对暂停截图重新检测。
   - 否则走 `DETECTION_PROVIDER` 实时检测，写 `outputs/<frameId>/`
2. `POST /api/feed/select-object`  
   - 视频预处理对象优先使用 `deduplicatedCropUrl`；没有映射时才回退帧内 bbox crop。
   - 去重 crop → Seedream 单张 45° 参考图 → Hunyuan / Tripo 单图生 3D 任务。
   - 返回 `glbUrl` + `generation`（brief / 参考图轨迹）
3. `POST /api/feed/run-pipeline` = detect + select（`objectId` 可空，默认第一个）

### F. 离线视频预分析（为比赛 Feed 准备缓存）

1. `POST /api/video/preprocess` → `outputs/videos/<videoId>/analysis.json`  
2. 支持 `reuseExistingFrames=true`，直接读取 `outputs/videos/<videoId>/frames.json` 和 `frames/` 下人工筛好的帧，不再自动抽帧。
3. CLIP 去重会把 `deduplicatedObjectId` / `deduplicatedCropUrl` 回写到组内每个帧对象。
4. Ark 对每个去重候选 crop 只估算一次合理尺寸。内部先获得合理范围，最终只保存“各轴下限 + 0.10m（不超过该轴上限）”得到的固定 `widthM/depthM/heightM`，单位为米，并同步到该组所有帧对象。它是初始缩放参考，不是真实测量值。
5. 之后 detect 走暂停帧匹配缓存：只比较暂停点前后两张已分析帧。

### G. 人工筛帧 + 暂停识别测试

1. 打开 `/static/frame-selector.html`，选择本地视频，例如 `2.mp4`，页面默认 `videoId=2`。
2. 在视频播放过程中暂停并保存需要参与后续识别的关键帧。
3. 保存结果写入：

```text
outputs/videos/<videoId>/frames/frame_t000012345ms.jpg
outputs/videos/<videoId>/frames.json
```

4. 再打开 `/static/pipeline-test.html`，选择同一个视频，点击“识别已有抽帧”。
5. 页面会调用 `/api/video/preprocess`，并带上：

```json
{
  "videoId": "2",
  "mode": "ark_grounding",
  "reuseExistingFrames": true
}
```

6. 预处理成功后，播放同一视频并暂停；页面计算暂停画面的 64-bit dHash，后端在前后两张已分析帧中选择更相似的一张，并把可点击 Tag 直接叠加到视频画面。

Base：`http://127.0.0.1:8000`

### 视频输出目录约定

单个视频的预处理、识别、去重和暂停后生成产物都应留在该视频目录下，例如 `videoId=2`：

```text
outputs/videos/2/
  frames/                 # 人工筛帧或自动抽帧
  frames.json             # 帧时间点清单
  analysis.json           # 逐帧检测 + 去重结果
  objects/                # 预处理阶段每帧检测出的 crop/mask
  deduplicated/           # CLIP 去重后的候选代表图
  generated/2_000001/     # 暂停匹配到某帧后，选物生成 3D 的中间产物和 GLB
```

注意：老的单图/兜底实时检测可能使用 `outputs/<frameId>/`；视频预处理帧 ID 形如 `<videoId>_000001` 时，后续生成目录应映射到 `outputs/videos/<videoId>/generated/<frameId>/`。

### `GET /health`

存活检查。

### `POST /api/feed/detect`

暂停视频时，前端传 `frameHash`；图片识别或无缓存实时检测仍可使用 `frameImage`。如果该 `videoId` 已有 `analysis.json`，后端不会重新检测暂停帧。

**Request**

```json
{
  "videoId": "living_room_001",
  "time": 12.4,
  "frameHash": "0f1e2d3c4b5a6978"
}
```

**Response（节选）**

```json
{
  "frameId": "frame_living_room_001_12_40",
  "frameImageUrl": "/outputs/.../frame.jpg",
  "objects": [
    {
      "id": "obj_sofa_001",
      "label": "sofa",
      "name": "沙发",
      "confidence": 0.9,
      "bbox": [x1, y1, x2, y2],
      "tagPosition": [0.5, 0.4],
      "cropUrl": "/outputs/.../crop.png",
      "maskUrl": "/outputs/.../mask.png",
      "deduplicatedObjectId": "candidate_sofa_001",
      "deduplicatedCropUrl": "/outputs/videos/living_room_001/deduplicated/candidate_sofa_001/crop.jpg",
      "prebuiltGlbUrl": "/outputs/videos/living_room_001/generated/candidate_sofa_001/generated_model.glb",
      "estimatedDimensions": {
        "widthM": 1.9,
        "depthM": 0.95,
        "heightM": 0.85,
        "unit": "m",
        "source": "ark_category_prior",
        "isMeasured": false,
        "selectionRule": "range_min_plus_0.10m_capped_at_max"
      },
      "visualFeatures": {},
      "generationHints": {}
    }
  ]
}
```

`visualFeatures` / `generationHints`：Ark 检测阶段可写入，供后续 3D brief 复用（避免二次视觉调用）。
`prebuiltGlbUrl`：缓存文件存在时返回 URL，否则为 `null`。比赛前端以此控制 Tag 是否可点击，
不以 `deduplicatedObjectId` 是否存在作为可用判断。

### `POST /api/room/placement-check`

单家具摆放检查。请求携带 `candidate` 和完整 `scene`；暂未接真实户型时也可只传
`sceneId=demo_living_room` 使用 mock 房间。`enableAgents=false` 时不调用文本模型，但仍返回
4 项几何检查和确定性 `layout.moves`。

```json
{
  "sceneId": "demo_living_room",
  "candidate": {
    "id": "obj_sofa_001",
    "label": "sofa",
    "name": "沙发",
    "position": [0.6, 0.0, 0.5],
    "rotation": [0.0, 0.0, 0.0],
    "size": [2.0, 0.85, 0.9]
  },
  "enableAgents": false
}
```

`POST /api/room/spatial-check` 是兼容旧名；全屋和场景深化分别使用
`POST /api/room/room-layout`、`POST /api/room/scenario-advice`。

### `POST /api/product/mock-search`

测试链专用确定性商品召回。按家具 `label` 返回 3 个固定候选，响应始终包含
`source=mock_catalog`、`isMock=true`；不读取 IKEA 索引，不运行 CLIP，不代表真实同款。

```json
{
  "objectId": "obj_sofa_001",
  "label": "sofa",
  "name": "沙发"
}
```

### `POST /api/floorplan/reconstruct`

真实户型图识别与白模生成。前端使用 `image` 上传完整图片 Data URL；服务器测试可使用
`/sample_data/floorplans/*` 或 `/outputs/*` 下的 `imagePath`，任意绝对路径会被拒绝。

```json
{
  "image": "data:image/jpeg;base64,..."
}
```

产物：

```text
outputs/floorplans/<sceneId>/
  original.png
  ai_input.jpg
  ai_raw.json
  normalized_scene.json
  whitebox.glb
```

返回 `sceneUrl`、`whiteboxGlbUrl`、`aiRawUrl`、`originalImageUrl` 和识别 warnings。
`knownLength` 本轮只记录、不参与比例校准。墙高固定 `3.0m`，墙厚固定 `0.1m`。

### `POST /api/floorplan/build-whitebox`

请求体直接使用 `FloorplanWhiteboxScene`，不调用 Ark，适合 JSON 人工修正和离线回归。
它会校验墙与门窗 ID、零长度墙、构件墙引用和构件边界，再生成标准 GLB。

### `GET /api/floorplan/presets`

返回比赛专用 `room1–7` 清单，包括 `sceneId`、原图 URL、SHA-256、结构 JSON、白模 GLB 和
`quality`。当前 `quality=placeholder`；每个预设指向各自 `preprocessed/<sceneId>/` 目录，现有七套
GLB 是根目录 `whitebox.glb` 的逐字节副本。

重新生成占位预设：

```powershell
python scripts/preprocess_floorplan_presets.py --mode placeholder
```

Ark 恢复后可用 `--mode ark` 单套或批量替换；单套失败会保留已有 placeholder。

### `GET /api/floorplan/presets/{sceneId}`

Space 刷新和直达时恢复单个户型资源。未知 `sceneId` 返回 404。

### `GET /api/feed/prebuilt-asset?frameId=...&objectId=...`

只从预分析对象解析 `deduplicatedObjectId`，并查找
`outputs/videos/<videoId>/generated/<candidateId>/generated_model.glb`。返回家具 GLB 与
`estimatedDimensions`；无缓存返回 404，**不会**调用识别、生图或 3D Provider。

`frameId` 必须能映射回 `outputs/videos/<videoId>/analysis.json` 中的对象；不要只把
`prebuiltGlbUrl` 从 Feed 带到 Space 后直接信任 URL，Space 刷新恢复依赖此接口完成校验和解析。

仓库的 `.gitignore` 与 `.dockerignore` 只对白名单开放视频 2 顶层
`generated_model.glb`，不会把 provider 任务日志、临时尝试或其他运行产物带入部署镜像。

白模 Builder 新生成的 GLB 节点会写入 `extras.rombotKind` 和 `extras.wallId`；墙节点还包含
`wallStart/wallEnd`，门窗包含 `fixtureId`。这些元数据供 Three.js Viewer 做自动墙体剖面。
比赛现有 `whitebox.glb` 未重建，前端通过 `wall_*_block_*` 名称和几何位置兼容。

## 7. 建议优化切入点（按收益）

1. **比赛资产覆盖**：逐个检查 `room1–7`、Feed 视频对象、`prebuiltGlbUrl`、尺寸元数据和部署白名单；缺缓存的 Tag 会被禁用，这是最直接的演示缺口。  
2. **白模质量**：当前七套预设仍是 placeholder，优先替换为各户型独立白模，并保留稳定的墙体 `wallId` / Builder extras，避免影响自动剖面。  
3. **Space 编辑能力**：目前变换只在当前页面内存中，可增加摆放持久化、撤销/重做、碰撞与贴墙/落地约束。  
4. **自动剖面**：继续用四个环绕方向、俯视、门窗和真实新白模回归；复杂内墙可能需要多墙剖面或房间分区策略。  
5. **移动端**：手机端测试当前停用；恢复后重点验证上传/拍摄、视频暂停、Tag 点击区域、WebGL 内存和触控手势冲突。  
6. **冷路径时延**：`feature_*` 串行 brief → Seedream → 3D 轮询；如重新接入实时生成，可拆提交/查进度 API、并行多物体并强化缓存。  
7. **冷路径质量/成本**：按品类优化 prompt、分割和尺寸估算，并在 Tripo / Hunyuan 间做质量-成本路由。

## 8. 已知坑

- **不要提交** `.env`、带签名云 URL 的 result JSON、大 GLB。  
- `hy-3d-3.1` **不支持** `LowPoly`；专业低模用 `hy-3d-3.0` + `HUNYUAN_GENERATE_TYPE=LowPoly`。  
- `hy-3d-express` **不要**传 `generate_type` / `face_count`（代码按模型分支处理，改 payload 时小心）。  
- Seedream 只生成 `reference_oblique_3quarter.png`；原 crop 不直接提交 3D，Hunyuan / Tripo 使用最后一张参考图。
- TokenHub 免费额度耗尽且未开通后付费时会返回 HTTP 402，需要在控制台“在线推理服务”开启后付费。
- `room_scan_standalone` 非主仓库交付物；主路径以 `backend` API + provider 为准。
- 比赛上传只接受与 manifest **逐字节 SHA-256 一致**的 `room1–7` 原图；截图、转码、压缩或加 EXIF 后都会匹配失败。
- `sceneId` 必须贯穿 `/space → /feed → /space`；丢失后用户需要重新选户型。
- 家具 Tag 可点击性依赖磁盘上的 `generated_model.glb`。新增 analysis 对象但未补 GLB，只会展示不可点击 Tag。
- 前端构建后再启动/刷新 FastAPI；`frontend/dist` 不存在时 FastAPI 不会注册 SPA fallback。
- 旧比赛白模缺少 Builder extras，自动剖面依赖节点命名兼容；重命名 `wall_*_block_*` 会破坏分组。
